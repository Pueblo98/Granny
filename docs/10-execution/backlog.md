# Prioritized Backlog

## Now — build the development-readiness package

- [ ] Run the [Astra Stage 1 development-readiness mission](astra-stage-1-planning-metaprompt.md) through every required workstream; its deliverable is the completed documentation system, not an audit report.
- [ ] Write and cross-link the comprehensive Stage 1 PRD, product model,
  proposed MVP/App V1 scope, signature use cases, and journeys.
- [ ] Write the canonical product design specification and detailed first Figma
  execution brief.
- [ ] Complete the agent/device-control, autonomy, confirmation, memory,
  recovery, privacy, family/helper, and safety contracts.
- [ ] Complete Stage 1 Android architecture and current Android/AccessibilityService/Google Play feasibility research.
- [ ] Complete canonical evals, failure taxonomy, and end-to-end requirements traceability.
- [ ] Create the research program, Stage 1 roadmap, milestone gates, Definition
  of Ready, and development-readiness assessment.
- [ ] Tighten `AGENTS.md`, `CLAUDE.md`, navigation, templates, and ADR links to
  make future agents maintain the finished system.
- [ ] Review the resulting proposed product choices with Simon and explicitly
  accept, revise, or defer only the consequential decisions.

## Next — evidence and interaction design after specification review

- [ ] Make the proposed MVP-scope decision using the completed PRD, feasibility
  evidence, and signature-flow comparison.
- [ ] Build the low-fidelity Figma package for the selected journeys, including
  voice/touch, ambiguity, confirmations, interruption, recovery, and degraded states.
- [ ] Explore 3–4 warm, calm visual directions only after interaction structure
  is reviewable.
- [ ] Run older-adult and trusted-family discovery/concept research using the
  approved consent and synthesis plan.
- [ ] Inventory the physical Samsung reference tablet without recording device
  identifiers or personal data.
- [ ] Test semantic observation/action/verification on the bounded synthetic-account app matrix.
- [ ] Validate candidate distribution paths and AccessibilityService posture.
- [ ] Benchmark current assistants against canonical evals with versioned raw evidence.
- [ ] Update proposed requirements, targets, ADRs, and gates from observed evidence.

## Then — controlled implementation after gates pass

- [ ] Start the first bounded vertical slice named in the development-readiness
  assessment, with linked PRD, journey, architecture, safety, and eval IDs.
- [ ] Build the smallest controlled device-action prototype using synthetic accounts and a safe-stop boundary.
- [ ] Add executable eval fixtures, structured traces, and regression reporting.
- [ ] Prototype memory consent/provenance only if it survives the MVP/App V1 scope decision.
- [ ] Investigate managed-device capabilities only from measured stock-Android gaps.
- [ ] Begin an MVP build only after its implementation-readiness gates pass.
- [ ] Revisit custom OS or dock/hardware only after Simon explicitly activates
  Stage 2 or Stage 3.

The final item above is Stage 3 context and remains dormant until Simon
explicitly activates that stage.
